# Архитектура ADEM

> Документ описывает **как** устроен проект. Идея и механики — в `GAME_DESIGN.md`, статус — в `ROADMAP.md`.
> Данный документ следует дополнять при значимом изменении структуры файлов.
> Статус в файле `ROADMAP.md` следует так же проверять и обновлять.

## 1. Общая картина

Проект — одно приложение на Rust (edition 2024) + Bevy 0.20 (`bevy` с `default-features = false`, включены `2d`, `ui`, `audio`, `system_clipboard`, `bevy_anti_alias`, `smaa_luts`, `zstd_rust`, `sysinfo_plugin`). Четыре модуля верхнего уровня:

- `simulation/` — правила и данные мира. **Без Bevy.** Детерминированно, однопоточно.
- `rendering/` — рисует мир, читая данные симуляции. Источник истины — только симуляция.
- `ui/` — панели, меню, ввод. Отдаёт команды симуляции, читает данные для отображения.
- `app/` — связывает всё: запуск, ресурсы, системы, фикс-степ тик, аудио, сохранения, настройки.

Bevy-ECS живёт только в `app/`, `rendering/`, `ui/`. В `simulation/` запрещены импорты `bevy::*`.

Прочие зависимости: `image` (png), `winit` (иконка окна — в Bevy 0.20 `Window::icon` удалён), `serde`/`serde_json`, `rand`; в `build.rs` — `winresource` (иконка exe на Windows), в dev — `naga` (тест синтаксиса шейдера). Профили: dev `opt-level = 1`, release `opt-level = 3` + `lto = "fat"` + `codegen-units = 1`, profiling (наследует release; без LTO, с линейными таблицами — для `cargo flamegraph --profile profiling`).

> **Платформы и распространение.** Целевые ОС — Windows и Linux. После рабочего прототипа — альфа на itch.io (бесплатно, добровольные пожертвования). Моддинг пока не планируется; редактируются только `data/` автором.

## 2. Симуляция

### 2.1. Модули

- `tile.rs` — `TileType` (15 вариантов, `repr(u8)`: …Mountain, Moss, Mud, Podzol), `ResourceKind`, плоский view `Tile`. Новые варианты — **только в конец** (стабильные дискриминанты для сохранений). Мох появляется пятнами в лесу при генерации; грязь и подзол — заделы под будущие биомы, замедление грязи — в `movement.rs`.
- `chunk.rs` — `Chunk`, слои, сжатие `TerrainTiles`. `ChunkPos` — `Hash`.
- `actions.rs` — **действия существа в мире**: движение (`step_direction`), добыча/посев/пахота (`interact`, `sow`, `harvest_crop/apple`), еда (`eat_selected` + `tick_hunger`), предметы (`pickup_item`, `drop_item`, `throw_selected/stack`), строительство (`build`), `reachable` (радиус `INTERACT_REACH = 2.0`). Все функции адресованы `SimEntity` по id (`(world, actor, …)`) и работают только у существ с «умом»; движение — у любых. Команды `Player*` и ИИ людей вызывают одни и те же функции — правила едины для захваченного существа и NPC.
- `combat.rs` — боевая система: ближний бой существа-актора (`try_melee_attack(world, actor, …)`: урон/кулдаун/дальность по предмету, рука = 1.0; сам атакующий попадать не может; `attack_entity` — удар по конкретному существу для ИИ охоты; `wolf_bite` — укус захваченного волка по точке прицела: волчьи характеристики, кулдаун на сущности и общий с ответными кусами ИИ `next_bite_tick`), снаряды (`Projectile` со стрелком `shooter`: стрела, брошенное копьё — баллистическая дуга, попадания по высоте ≤ 1 тайла, стрелок исключён), воткнутые копья (`StuckSpear` — «мини-сущности» с автоподбором в радиусе 1 тайла захваченным существом). Смерть — `kill_entity` (дроп лута + удаление); инвентарь человека падает целиком. Характеристики оружия — `ItemKind::weapon_stats` (нож 5.0/6 тиков, копьё 5.0/10, топор 7.0/15; лук стреляет — 10.0, 20 тайлов, 15 тиков).
- `hunger.rs` — голод как **общая потребность существа** (`Hunger` + `Activity`): существо хранит `Hunger` на `SimEntity` (все виды, включая волка и кролика) и на своём тике вызывает `tick(activity)`, применяя возвращённый урон к своему hp. Расход за тик: стояние 0.0005, ходьба 0.004, плавание 0.006; при голоде < 5.0 — 1.0 урона раз в 50 тиков; еда — `eat(food_value)`. Кулдаун поедания — `EAT_COOLDOWN_TICKS = 50`. Пассивная регенерация: при сытости > 80.0 и неполном HP — 2.0 сытости раз в 200 тиков за 1.0 HP (полное HP — скип). Потребители — все существа: автономные тикают голод в общем FSM (`EntityStore::update`, смерти от голода — в `tick_entities`), захваченное — app-слой; O(1) на существо, планировщик не нужен. Еда волка — мясо с земли (`ItemKind::is_wolf_food`), см. `item_entity.rs`.
- `armor.rs` — броня как **общая система**: `protection_of(ItemKind)` — защита предмета (кольчуга 3/4/3/2 по шлем/кираса/поножи/ботинки), `rating(&Inventory)` — сумма по надетым слотам брони (0–100; предмет в misc/мусорке не надет), `reduce_damage(rating, damage)` — линейное поглощение (сколько поинтов — столько % урона снято). Потребителей урона пока нет — основа под бой.
- `clothes.rs` — одежда как **общая система** (задел под холод/погоду): `warmth_of(ItemKind)` — тепло предмета, `warmth(&Inventory)` — сумма по надетым слотам одежды (0–100, считаются только слоты одежды). Предметов одежды пока нет, потребителей тепла тоже — основа под потребность «Температура».
- `world.rs` — `World`, `WorldSize`, `TilePos`/`ChunkPos`/`WorldPos` (непрерывные координаты сущностей), `TILE_SIZE = 16.0`, доступ к слоям; `World::tick_entities(tick, controlled)` и `World::tick_item_entities(tick)`.
- `objects.rs` — два класса видов над тайлом: **Объекты** (`ObjectKind`: Tree, Bush, Rock, AppleTree — природные, генерируются) и **Постройки** (`BuildingKind`: Campfire, CraftingTable, Furnace, Barrel, BlastFurnace, Storage, SmithingTable — рукотворные, строятся игроком/редактором). Хранение единое: `ObjectKind::Building(BuildingKind)` — один слой чанка, кодировка дискриминантов для сохранений (природные 0–3, постройки 4 + вид постройки). `ObjectStage`, `WorldObject`, `build_cost(BuildingKind)` (цена задана только у костра — остальные станции строятся редактором). `is_station()` — станции с GUI; контейнер станции создаётся/удаляется вместе с объектом (`World::set_object_with_container`).
- `generation.rs` — процедурная генерация (собственный value-noise, без внешних крейтов).
- `dirty.rs` — `DirtyTiles`: изменённые тайлы по каналам причины — `terrain` (рельеф: рендер пересобирает меш блока) и `decor` (объекты/предметы: рендер обновляет только дочерние спрайты блока). Обычные данные без Bevy: канал наполняют команды и растительность, изымает рендер.
- `vegetation.rs` — самозапланированные процессы мира.
- `crops.rs` — культуры на пашне: `CropKind` (Wheat, Beetroot, Carrot, Potato, Cherry; стадий 8/4), `Crop { kind, stage }`. Полный цикл — 3 игровых месяца (`GROWTH_CYCLE_TICKS`), интервал стадии = цикл/(стадий−1). Рост — цепочка `TaskKind::CropGrowth` (зимой замирает до весны); сажаются семенами (пшеница, свёкла) или самим плодом (морковь, картофель, вишня); урожай детерминированный. Пустая пашня (без культуры) задачей `FarmlandRevert` через месяц возвращается в землю.
- `containers.rs` — контейнеры станций: `Container { slots, cook_finish_tick, burn_out_tick, burning_fuel }` в разреженном слое чанка. Раскладки слотов константами (печь 5, плавильня 7, бочка 24, склад 16, костёр 2); правила слотов — `can_put_into` (выход/отходы — только забирать, плавильня жжёт только Coal). Рабочий цикл печей — событийный: абсолютные тики готовки/прогорания, задача `TaskKind::StationTick` на ближайшее событие; время готовки 100 тиков (печь), 200 (плавильня, костёр); топливо — `ItemKind::burn_time()`; прогоревшее топливо оставляет PitAsh с шансом 40% (уголь 25%). `wake_station` — поджиг после ручной смены слотов.
- `time.rs` — константы календаря, `GameClock`, `Season`.
- `climate.rs` — температура окружения как чистая функция календаря: среднемесячные базы умеренного климата (индекс согласован с `Season::from_month`) с интерполяцией между месяцами + суточный ход (косинусоида, пик в 15:00). `ambient_temperature_c(tick)` детерминирован тиком.
- `scheduler.rs` — `Scheduler` (bucket + heap). Мировые задачи: растительность (`GrassSpread`, `BushGrowth`, `WaterErosion`), культуры (`CropGrowth`), станции (`StationTick`), заделы (`ObjectGrowth`, `NeedThreshold`).
- `commands.rs` — `Command`, `CommandQueue`. Кроме 13 базовых: `PlayerSow` (посев культуры), `PlayerThrowItem` (бросок одного предмета из выбранного слота по бинду «Бросить предмет») и `PlayerThrowStack` (бросок стека из слота misc — перетаскивание за пределы GUI); оба летят до 3 тайлов в сторону курсора с замедлением (ease-out, `ItemEntity::fly` — транзиент, в сейв не пишется) и лежат с задержкой автоподбора 50 тиков (`item_entity::THROW_*`); Shift/Ctrl + бросок выкидывает весь слот, `StationMoveItem { pos, from, to, count }` (перенос между контейнером станции и misc игрока; адрес (0xFF, i) — misc, (слот, 0) — станция; count 0 = весь стак; merge/swap). `buildable_at` отклоняет тайлы с культурами; `SetObject`/`PlayerBuild` ведут контейнер станции и снимают культуру под объектом.
- `ai.rs` — автономное поведение людей (ИИ выживания): голод → еда из инвентаря/яблони/культуры/охота; ночь → костёр (радиусы и константы в шапке модуля); иначе брожение. Работает поверх общего FSM (`entities.rs`), выставляя цели; решения детерминированы (`decision_rng`). Захваченное существо ИИ не ведёт.
- `entities.rs` — `SimEntity` (+ `HumanMind`/`HumanGoal`), `EntityStore`, FSM поведения.
- `items/` — каталог и инвентарь: `catalog.rs` — `ItemKind` (91 вид), `ToolClass`/`WeaponStats`; `mod.rs` — `ItemStack`, `Inventory`, слоты и правила размещения. `tool_class()` — обобщённая проверка инструментов (кирка добывает камень, мотыга пашет — идея Minecraft); `burn_time()` — горючесть топлива; `food_value()` — питательность еды (0 — несъедобное), поедание обобщено на любую еду. Последние виды: BeetrootSeeds, Beetroot, BeetrootRoasted, Cherry, Coal, Charcoal, Torch.
- `movement.rs` — **общие правила движения существ**: модификаторы рельефа (`WADE_SLOWDOWN = 3.0`, `MOUNTAIN_SLOWDOWN = 2.0`), `terrain_speed_multiplier` и `effective_walk_speed`. Базовая скорость — параметр существа (у вида — `EntityKind::walk_speed`, у игрока — `PLAYER_WALK_SPEED`), рельеф замедляет всех одинаково. Новые модификаторы (грязь, снег, растительность) добавляются только сюда.
- `crafts.rs` — `CraftBook`, `CraftRecipe`, `CrafterKind` (рекурсивная загрузка `data/crafts/**`; `parent` в JSON задаёт группу крафтера: `manual`, `crafting_table`, `smithing_table`, `campfire`, `furnace`, `blast_furnace`; папка — организация и проверка раскладки). Рецепты индексируются по группам: `matching_recipe_for(crafters, grid, held_tools)` смотрит только свою группу и проверяет `tools` (кузнечный стол, инструменты не расходуются); `cooking_recipe(crafter, input)` — O(1) для печей и костра.
- `item_entity.rs` — дроп-сущности (MC-стиль): `ItemEntity { id, pos, stack, spawn_tick, pickup_after_tick }` в `World.item_entities`. Дроп с разбросом и слиянием стеков, автоподбор **ближайшим человеком** (`World::tick_item_entities`: O(дроп × едоки)) в радиусе 0.75 тайла после задержки, despawn через 7200 тиков. В том же проходе голодные волки едят мясо с земли (`is_wolf_food`): единица за тик в радиусе 0.75 тайла, без инвентаря; голодный волк идёт к ближайшему мясу в 16 тайлах (`World::tick_fauna`). Бросок (`PlayerThrowItem`/`PlayerThrowStack` через `actions::throw_*`) кладёт сущность в 3 тайлах от бросающего в сторону курсора с задержкой подбора 50 тиков. Источник — дроп с погибших существ (`combat.rs`); слой предметов на тайлах (`Chunk.items`) — отдельная механика, не затронута.
- `needs.rs` — lazy-потребности (готовая механика, потребителей пока нет).
- `save/` — бинарные сохранения: `write.rs` (сериализация), `read.rs` (разбор), `validate.rs` (структурные проверки формата), `mod.rs` — формат, ошибки, заголовок.
- Публичный API реэкспортируется из `simulation/mod.rs`; остальные слои вызывают симуляцию только через него.

### 2.2. Мир и слои чанка

`World` хранит `size`, `seed`, `chunks: Vec<Chunk>` (row-major), `entities: EntityStore`, `ambient_temperature_c`. `WorldSize` зажимает сторону в [256, 16384] с округлением до кратности 16. Адресация: `split_tile(pos) -> (ChunkPos, u8)` и обратная `tile_pos(chunk, idx)` — публичная пара для задач планировщика.

`Chunk` — 16×16 тайлов, четыре независимых слоя:

```rust
pub struct Chunk {
    pub terrain: TerrainTiles,
    pub resources: HashMap<u8, ResourceDeposit>, // ключ — линейный индекс тайла 0..256
    pub objects: HashMap<u8, WorldObject>,       // один объект на тайл
    pub items: HashMap<u8, ItemStack>,           // предметы на земле
    pub crops: HashMap<u8, Crop>,                // культуры на пашне
    pub containers: HashMap<u8, Container>,      // контейнеры станций
}
```

- **`TerrainTiles`** — `Uniform(TileType)` или `Full(Box<[TileType; 256]>)`. Первый отличающийся тайл разворачивает `Uniform → Full`; `try_compress()` схлопывает обратно (после генерации, при сохранении).
- **Разреженные слои** (`HashMap`) выбраны из соображений ОЗУ: объектов ~1% тайлов, ресурсов и предметов ещё меньше.
- Горячие пути (меш, генерация) обходят рельеф напрямую через `TerrainTiles`, минуя сборку view.
- `Tile` (плоский view из трёх полей) остаётся для UI/тестов; `World::set_terrain/set_resource/set_object/set_item` — точечные сеттеры симуляции.

### 2.3. Время и календарь

Константы в `simulation/time.rs`:

- `TICKS_PER_SEC = 20` (реальных тиков в секунду на x1), `GAME_SECS_PER_TICK = 12`.
- Сутки 24 ч (`TICKS_PER_DAY = 7200`), месяц 15 суток, сезон 3 месяца, год 12 месяцев.
- Производные: `TICKS_PER_MONTH = 108_000`, `TICKS_PER_YEAR = 1_296_000`.

`GameClock { tick: u64 }` — календарь вычисляется по запросу (`year()`, `season()`, `hour_of_day()` и т.д.). Свободные функции `next_hour_tick` / `next_season_tick` дают тики строгих границ для календарных событий. `Season::from_month` — месяц/3 % 4 (весна = месяцы 1–3). Новый мир начинается в `START_HOUR_OF_DAY` (8:00): `start_tick()` — стартовый тик, от него же сеются календарь и растительность.

### 2.4. Планировщик

`Scheduler` — центральная очередь по тикам, **никаких опросов мира каждый тик**:

- **`near: Vec<Vec<Task>>`** — кольцевой буфер на `NEAR_WINDOW = 64` тиков, бакет = `tick % 64`.
- **`far: BinaryHeap<Reverse<(tick, id, Task)>>`** — дальние события; при исполнении переносится в окно.
- **`cancelled: HashSet<TaskId>`** — ленивая отмена: id пропускается при исполнении.
- `TaskId` выдаётся последовательно; бакет сортируется по id — стабильный порядок при равных тиках. `run_tick` продвигается по одному тику даже при перескоке.
- **Планировать новые задачи изнутри `run_tick` нельзя** — исполненные задачи собираются в список и обрабатываются вызывающим (app-слой) после.
- `clear_world_tasks()` удаляет задачи мира (растительность, потребности), сохраняя календарные — используется при перегенерации мира.

`TaskKind`: календарные (`TimeOfDayChanged`, `SeasonChanged`), растительность (`GrassSpread`, `BushGrowth`, `WaterErosion`), культуры и пашня (`CropGrowth`, `FarmlandRevert` — пустая пашня раз в месяц возвращается в землю), станции (`StationTick`), заделы (`ObjectGrowth`, `NeedThreshold`), `Marker` для тестов. Кодировка в сохранениях — явные теги, не порядок enum.

### 2.5. Растительность — процессы, а не опрос

`vegetation.rs` — образец event-driven подхода (GAME_DESIGN 4.4): каждое активное «место» живёт **цепочкой самозапланированных событий**. Событие применяет правило и планирует следующее; неприменимое правило гасит цепочку.

- Вероятности «за такт»: `GRASS_SPREAD_P = 0.0008`, `BUSH_GROW_P = 0.0002`, `EROSION_P = 0.0002`, предел `BUSH_CAP_PER_CHUNK = 24`.
- `interval_ticks(rng, p)` — интервал из геометрического распределения (среднее 1/p), средняя частота совпадает с вероятностной формулировкой.
- `event_rng(seed, tick, tag, chunk, local)` — RNG события сеется от координат и тика, состояние не хранится → воспроизводимо после загрузки сохранения.
- `seed_all` — однократный посев после генерации; `after_tile_changed` — перезапуск цепочек после правки тайла (редактор, игрок); `apply_task` — применение исполненных задач, изменённые тайлы уходят в dirty рендера.
- Правила: трава занимает соседа Dirt; чанк леса растит куст на ForestGrass; вода эродирует берега (ForestGrass→Grass, Grass/Dirt→Sand). Соседи — ортогональные 4.

### 2.6. Команды

`CommandQueue` (FIFO на `VecDeque`) — единый канал действий. Источники: редактор, захваченное существо («игрок»), (позже ИИ и «бог»). Варианты `Command`:

- Инструменты «бога»: `SetTerrain`, `SetObject` (в т.ч. удаление), `SpawnEntity`, `RemoveEntity { id }` (id, не тайл), `MoveEntity { id, pos }` (перетаскивание существа в редакторе), `EntityMoveItem`/`EntityDropItem` (инспектор: перенос стека в инвентаре существа / выброс на землю).
- Действия захваченного существа (`Player*`): `PlayerInteract` (бой или добыча), `PlayerBite` (укус неразумного существа — единственное действие ЛКМ волка, только бой), `PlayerBreakBuilding` (ломание постройки зажатием ЛКМ: команда каждый кадр зажатия, `actions::break_building` копит тики непрерывности — 80 тиков рушат постройку с дропом цены и содержимого контейнера; прогресс транзиентен, `World.building_breaks`), `PlayerHarvestApple`, `PlayerDropItem`, `PlayerDropStack`, `PlayerPickupItem`, `PlayerBuild` (плата списывается симуляцией после проверки места), `PlayerThrowSpear`, `PlayerShootBow`, `PlayerSow`, `PlayerEat`, `PlayerThrowItem`/`PlayerThrowStack`. Команды исполняет **захваченная сущность**: `apply_all(world, actor: Option<u64>, …)` резолвит её по id и вызывает общие `actions::*` (в наблюдателе `actor = None`, действия пропускаются).
- Станции: `StationMoveItem` — misc захваченного существа адресуется `(0xFF, i)`.

`apply_all` вызывается app-слоем **каждый кадр** (редактор работает на паузе), порядок = порядок постановки. После каждого изменения тайла вызывается `vegetation::after_tile_changed`. Публичная `buildable_at(world, pos)` — единая проверка места для симуляции и голограммы рендера. Дроп на занятый тайл ищет свободный кольцами до края мира.

### 2.7. Захваченное существо (режим игрока)

Отдельного игрока в мире **нет** (целевой формат GAME_DESIGN 4.1 реализован): существо «человек» — обычная сущность мира, а режим игры — это **захват** существа контроллером. Состояние захвата — `GameState.controlled: Option<u64>` (id в `EntityStore`); `GameMode::Player` ⇔ `controlled.is_some()`, меняется только через `set_controlled` (F1 по сущности под курсором — захват, повторный F1 — отпускание; смерть/удаление существа возвращает наблюдателя). Захват/отпускание сбрасывают FSM-движение существа в стояние. Доступ UI — `controlled_entity()/controlled_mind()` в `app/state.rs`. Кнопка «ИИ» в правом нижнем углу (`GameState.controlled_ai`, по умолчанию выкл.) передаёт захваченное существо общим правилам мира: FSM/ИИ ведут его сами (движение и голод — симуляция, `step_direction`/`tick_hunger` в этот момент не вызываются, чтобы голод не тикал дважды).

- Движение: `actions::step_direction(world, actor, dir)` на тике — ввод преобразуется в диагональные оси изометрии (`player_grid_dir`), нормализуется; по осям скольжение вдоль берега; DeepWater/Ocean непроходимы, кроме случая, когда существо уже стоит в глубине.
- Голод: `actions::tick_hunger` на каждом тике (Activity из рельефа и движения); hp ≤ 0 — смерть: `combat::kill_entity` дропает инвентарь item-сущностями, захват снимается.
- Все возможности (добыча, крафт через UI, станции, строительство, бой) — те же `actions::*`/команды, что и у автономных людей; UI (хотбар, инвентарь, строительство, станции) работает с инвентарём захваченного существа. У неразумного захваченного (волк) — движение и укус по ЛКМ (`PlayerBite`), без UI инвентаря.

> **Отношение к NPC-системам.** Модули `hunger`, `armor`, `clothes`, `needs`, `combat`, `movement`, `actions` — общие и не содержат специфичных для игрока правил; индивидуальна только базовая скорость существа. Разница между «игроком» и NPC — только источник команд: контроллер или ИИ (simulation/ai.rs).

### 2.8. Существа

`entities.rs`. `EntityStore` — `Vec<SimEntity>` (детерминированный порядок), id с 1, не переиспользуются; `get/get_mut(id)`.

- `EntityKind`: `Wolf` (hp 80), `Human` (hp 100) и `Rabbit` (hp 40, скорость 0.18 тайла/тик); новые виды — **в конец** enum (стабильные дискриминанты). `is_sentient()` — у кого есть «ум».
- `SimEntity`: id, `pos`/`prev_pos`, facing, state, hp, `hunger: Hunger` (общая потребность всех видов), `water_ticks`, `state_ticks`/`state_duration`, target, `stuck_ticks` и `mind: Option<HumanMind>` — «ум» разумного: `inventory` (8 misc + 4 брони + 4 одежды + 4 косметики + мусорка), `selected_slot`; transient — кулдауны атаки/еды, цель ИИ `goal: HumanGoal` (Campfire/Food/Hunt/Gather), память ИИ (`known_campfire`/`known_food`), `next_think_tick`, обида волка (`provoked_by`/`provoked_until_tick`/`next_bite_tick`), кулдаун выпаса кролика `next_graze_tick`. Волк и кролик — `None` (не платят памятью).
- FSM: `Standing → Walking | Lying` у животных (лежание с шансом `LIE_CHANCE = 0.2`); человек из стояния не бродит сам — его ведёт ИИ. Общее: брожение в круге 8 тайлов (животные, прямая отсеивает только глубокую воду); у людей брожение и дневные сканы требуют сухую цель и не больше 2 проб воды на пути (узкая река — можно, озеро — нет), движение по осям со скоростью вида и модификаторами рельефа (`movement.rs`), паника в глубокой воде и BFS к суше (лимит 40 000 тайлов), голод всех существ (смерти от голода исполняет `tick_entities` через `kill_entity`).
- Взгляд: `facing` меняется только при экранно-горизонтальном движении или цели — `entities::screen_facing(dx, dy)` по знаку `dx − dy` в осях сетки. Экранная вертикаль (сеточная диагональ (+1,+1)/(−1,−1)) взгляд сохраняет; правило общее для ввода игрока, FSM, ИИ и атаки.
- Волк: выживший после удара запоминает обидчика (`provoke_wolf` в `combat.rs`) на 5 секунд — кусает на 8.0 в досягаемости (кулдаун 1 с) или убегает на 10 тайлов прочь (`tick_wolf_provocations`). Голодный волк (сытость < 60) охотится на кроликов: кусает в досягаемости, иначе идёт к мясу на земле, иначе к ближайшему кролику в 16 тайлах (`tick_fauna`).
- Кролик: травоядное — при голоде (< 80) ест траву под собой (+15 сытости, кулдаун 50 тиков, тайл не меняется) или идёт к ближайшей траве в радиусе 8 тайлов; волка в радиусе 6 тайлов замечает и убегает. Три прыжковых кадра ходьбы, смена раз в 5 тиков.
- Детерминизм: `decision_rng(world_seed, entity_id, tick)` — splitmix-хэш, состояние RNG не сохраняется.
- `World::tick_entities(tick, player_controlled)` — общий FSM (захваченное существо FSM не ведёт: движение, взгляд и состояния Walking/Standing задаёт `actions::step_direction` по вводу), затем `tick_wolf_provocations` и `tick_fauna` (охота волков, побег и выпас кроликов; снимки позиций один раз за тик, цель обновляется без сброса `state_ticks`), затем `ai::tick_human_ai`: автономное выживание людей: при голоде < 40 — еда из инвентаря (с кулдауном) → известная/найденная еда (яблоня с плодами, зрелая культура) → охота на волка; ночью (21:00–06:00) — идти к известному костру и стоять у него лицом к огню; днём без цели — запас еды впрок (< 85 сытости), сбор палок с кустов, осмотреться; иначе брожение. Поиск — по памяти («ходить и искать»): малые сканы (костёр 12, еда 10 тайлов) пополняют `known_campfire`/`known_food`, неактуальное забывается. FSM из стояния для людей ничего не решает (раньше вечный сброс стояния делал брожение недостижимым — люди простаивали). «Обдумывание» — не чаще раза в 5 секунд (`next_think_tick`), между обдумываниями только исполнение цели. LOD ИИ для тысяч людей — будущая работа (см. `ROADMAP.md`).
- Смерть существа — `combat::kill_entity`: дроп добычи (волк → мясо/кость; кролик → 1 сырое мясо травоядного; человек → весь инвентарь) + удаление.

> **Виды.** Разумные — только люди; волк и кролик — животные с общим набором систем (FSM, движение, восприятие). Новые животные добавляются в конец `EntityKind`; LOD существ (в будущем) — по критерию «пиксель спрайта меньше реального пикселя на экране»; архитектурно — упрощённая модель поведения на дальних чанках (детали в `ROADMAP.md`).

### 2.9. Предметы, инвентарь, крафт

`items.rs`:

- `ITEM_KIND_COUNT = 91`; `ItemKind` (`repr(u8)`) со стабильными строковыми id для JSON (`"stick"`, `"fishing_rod"`, …). `class()` — match без wildcard: новый вид предмета не скомпилируется, пока не решён его класс. Каталог: базовые ресурсы и инструменты, кости/перья/нити, бумага и книги, глина и кирпичи, семена и пшеница, самородки/слитки/самоцветы/порошки, еда, руды, каменный молот, медные инструменты и факел (жарка палки в костре).
- Первая броня — кольчужный комплект (без крафтов): шлем/кираса/поножи/ботинки, класс `Armor(slot)`, стак по единице; в чужой слот брони не кладётся (`accepts` по `ARMOR_LAYOUT`). Защита — в `armor.rs`. Одежда (класс `Clothes(slot)`, деление по частям тела как у брони) — задел: слоты и система тепла (`clothes.rs`) готовы, самих предметов пока нет.
- `ItemClass { Misc, Armor(BodySlot), Clothes(BodySlot), Bauble }`; части тела — общий `BodySlot { Head, Chest, Legs, Boots, Body }`. Слоты: `MISC_SLOTS = 8`, `ARMOR_SLOTS = 4`, `CLOTHES_SLOTS = 4`, `BAUBLE_SLOTS = 4` — compile-time assert'ы синхронизируют UI.
- `Inventory` (Copy): секции misc/armor/clothes/baubles + слот `trash` (мусорка UI удаления: принимает что угодно, каждая новая кладка затирает прежний стек, затёртый можно забрать до следующей кладки; в `SlotArea::ALL` и `count_of` не входит — предметы из мусорки не тратятся и не съедаются), `MAX_STACK = 64`. Предел стака — по виду предмета (`ItemKind::max_stack`, match без wildcard): инструменты и оружие — по единице на слот (и на тайл на земле, и в клетке крафта), расходники — до 64. Методы: `add` (долив стеков → пустые слоты с учётом предела вида, возвращает остаток), `can_fit`, `count_of`, `take_items` (атомарное списание со всех стеков — оплата строительства), `accepts`/`transfer` (правила размещения и drag&drop).

`crafts.rs` — рецепты целиком в данных (`data/crafts/*.json`):

- `parent` (строка или массив) — виды крафтеров, которым доступен рецепт: `manual`, `crafting_table`, `smithing_table`, `campfire`, `furnace`, `blast_furnace`. Папка файла — организация и подсказка раскладки: загрузчик проверяет, что она входит в `parent`, но при расхождении только пишет предупреждение в debug-лог (рецепт загружается). Верстак наследует `manual`, кузнечный стол — только свою группу.
- Две схемы: **сеточная** (`manual`/`crafting_table`/`smithing_table`) — shaped (по умолчанию) или shapeless; **кулинарная** (печи/костёр) — один `input` + `result`, без `shapeless`/`grid`. У shaped `ingredients` — объект «символ → предмет», `grid` — сетка 3×3 из символов/`null` (форма обрезается по занятым клеткам); у shapeless `ingredients` — массив `item + count`.
- `CraftBook::load_dir` — рекурсивный обход в лексикографическом порядке (детерминизм), ошибки файлов не роняют игру. Валидация: известные предметы/крафтеры, count > 0, сетка ≤ 3×3, символы описаны в `ingredients`, инструменты — известные предметы (≤ 4), дубликат `(крафтер, id)` — ошибка.
- В памяти: арена `recipes` + `groups` (индексы по крафтерам) + `cooking` (`предмет → рецепт`). `matching_recipe_for(crafters, grid, held_tools)` идёт по своей группе и возвращает первый подходящий; `consume(grid)` списывает ингредиенты; `max_crafts(grid, inventory)`/`try_craft_one` считают массовый крафт без аллокаций (стоимость и нормализованные ингредиенты посчитаны при загрузке).

### 2.10. Потребности (lazy, без потребителей)

`needs.rs` — законченная механика, потребителей пока нет (модуль `#![allow(dead_code)]`):

- `Need { value, since_tick, rate }` — хранится значение на тик последнего пересчёта; `value_at(now)` восстанавливает актуальное значение за O(1) **без тикания каждого существа**.
- `close()` фиксирует накопленное (перед сменой rate или сохранением), `ticks_until(threshold)` — через сколько тиков достигнут порог (None → задача в планировщик не ставится).
- Интеграция: `TaskKind::NeedThreshold { owner, need }` в планировщике, `NeedKind` сериализуется в сохранениях.

### 2.11. Температура

`ambient_temperature_c` в `World` — температура окружения, ℃. Считается из календаря (`simulation/climate.rs`): среднемесячные базы умеренного климата (−5…+23.5 ℃, месяцы согласованы с сезонами) с интерполяцией между месяцами плюс суточный ход (амплитуда 6 ℃, пик в 15:00). Обновляется app-слоем каждый тик (и на генерации мира); чистая функция от тика — планировщик не нужен. Пока ни на что не влияет (основа под погоду и потребности), отображается в FPS-панели.

### 2.12. Генерация

`generation.rs` — собственный value-noise (hash2 — splitmix-подобный хэш), один seed → одна карта:

1. **Рельеф + ресурсы**: fbm (5 октав) с domain warp и спадом к краям карты (край гарантированно под океаном); горы по гребневому шуму; биомы по шуму влажности. Ресурсы: медь на камне (p=0.10), глина на земле/траве (p=0.02, тайл становится Clay).
2. **Классификация водоёмов**: BFS от периметра — вода у края = море, внутренние регионы = озёра; регионы < 12 тайлов осушаются в песок. `BitGrid` — битовая карта (~33 МБ вместо 268 МБ на максимальном мире).
3. **Реки**: спуск по 8 соседям с отдельным RNG-потоком; ширина 1–3 тайла растёт от истока к устью; локальный минимум → залив котловины (потолок 512 тайлов).
4. **Объекты**: отдельный RNG-проход (не смешивается с рельефом). Лес: дерево 18%, яблоня 4% (4–10 плодов), куст 3%, валун 0.3%; трава: куст 3%; камень/гора: валун.
5. **Дикая природа**: волки с плотностью 1 на 8192 тайла (max 64), не в воде; кролики — 1 на 4096 тайлов (max 128) только на траве и лесной траве.
6. Финал: `try_compress` всех чанков.

Все обходы с фиксированным порядком соседей и row-major перебором — детерминизм в пределах платформы.

### 2.13. Детерминизм и RNG

- Один seed → одинаковая карта; RNG — seeded (`rand 0.10`), никаких `thread_rng`.
- Событийные и решающие RNG сеются от (seed, тик, координаты/id) — состояние не хранится и не сохраняется.
- Обход `HashMap` недетерминирован: всё, где порядок влияет на результат, ходит по `Vec`/отсортированным ключам.
- Сохранения дают **одинаковые байты** для одинаковых состояний (разреженные слои по возрастанию индексов, списки сортируются).

> Воспроизводимость **между платформами** (Windows/Linux) — желательна и планируется, но не обязательна на текущем этапе. Все источники недетерминизма (порядок `HashMap`, `thread_rng`, время) уже изолированы; при переходе к кроссплатформенной воспроизводимости остаётся только проверять арифметику float и порядок обхода контейнеров.

## 3. Сохранения

`simulation/save/` — бинарный little-endian формат без внешних крейтов, `SAVE_FORMAT_VERSION = 4` (v2: слои культур и контейнеров станций, item-сущности дропа, задачи CropGrowth/StationTick; v3: игрок стал сущностью — «ум» существ (инвентарь/слот хотбара) в записях существ, секция игрока удалена, у снаряда поле стрелка; v4: голод перенесён из «ума» на уровень существа — голодают все виды; сейвы v3 и старше не читаются), magic `b"ADEM"`.

- Заголовок: magic + format_version + версия игры (строка) + seed + tick + world_side. `read_header` читает только его — список слотов не парсит тело.
- Тело: мир (температура, чанки row-major: рельеф tag Uniform/Full + байты, разреженные ресурсы, объекты и **предметы на земле**), существа (записи по возрастанию id; у существ с «умом» — инвентарь всех секций, голод и выбранный слот; кулдауны и цель ИИ — transient), снаряды в полёте и воткнутые копья, планировщик (текущий тик, отменённые, бакеты). Координаты чанков в задачах валидируются при загрузке — битый файл даёт `BadData`, а не панику.
- Строгая валидация при загрузке: лимиты ёмкостей (защита от битых count), проверка дискриминантов, диапазонов HP/голода, пределов стаков, соответствия предметов секциям инвентаря (шлем в поножи = `BadData`), дубликатов, совпадения тиков заголовка и планировщика. Лишние байты в конце = повреждение.
- `SaveError { BadMagic, UnsupportedFormat, Truncated, BadData }`.
- **Не сохраняются**: transient-состояние UI (скорость, пауза) и кулдауны игрока (атака, еда).

`app/saves.rs` — `SavesPlugin`: 4 слота (`saves/save_N.adem`), сообщения `SaveGameRequest`/`LoadGameRequest`, обновление подписей слотов и `pending_rerender` при загрузке. Захват существа при загрузке сбрасывается (управление всегда начинается с наблюдателя).

> **Политика совместимости.** Для каждого релиза в `SAVE_FORMAT_VERSION` инкрементируется версия при несовместимых изменениях; в описании релиза указывается, совместим ли он с предыдущими сейвами. Автоматическая миграция сейвов не предусмотрена — при несовместимости старый файл даёт `UnsupportedFormat`. Все поля версионируются явными тегами, чтобы при необходимости можно было добавить миграцию точечно, без переписывания формата.

## 3.1. Бюджет памяти мира

Текущий технический лимит — ~6 байт на тайл в ОЗУ (заголовок чанка + `TerrainTiles::Full` + доля разреженных слоёв). При максимальном размере 16384×16384 это даёт сотни МБ, что и определяет текущий «потолок» карты.

Стратегия снижения (в будущем, `ROADMAP.md` → «Инфраструктура и качество»):
- Более плотная упаковка `TerrainTiles::Full` (битовое кодирование с палитрой на чанк).
- Отказ от хранения полного массива там, где достаточно `Uniform`-сегментов.
- Lazy-загрузка чанков из сейва по требованию (для далёких регионов, в которых ничего не происходит).
- Пакетное сжатие редко посещаемых чанков (компрессия в отдельном файле, распаковка на лету).

После каждого шага — замеры (см. 4.1 «Фикс-степ тик» и `TickTiming`).

Дальняя плоскость пересчитывается под размер мира каждый кадр (far, назначенный на старте для мира 256², резал дальний угол карт ~от 600 тайлов); на 3D-камере стоит `ClusterConfig::Single` (один кластер света на весь фрустум — реальных 3D-светов нет; вариант None сломан в bevy 0.20.1: dummy-текстура нулевого размера).
- `input/` — `PlayerInput`; состав: `player.rs` (захват, движение, ЛКМ/ПКМ, броски), `editor.rs` (удаление ПКМ, перетаскивание СКМ), `helpers.rs` (`cursor_world_pos`/`cursor_world_tile`, пикинг `entity_at`). F1 — **захват сущности под курсором** (радиус 2 тайла, `entity_at` — по альфа-границам фактической текстуры из `EntitySpriteVisuals`) / отпускание; WASD захваченного существа задаёт экранные направления, преобразованные в диагональные оси изометрической сетки; ЛКМ: размещение в редакторе / добыча с автоповтором 0.5 с в Player; ПКМ: удаление в редакторе (с порогом драга) / сбор предметов и яблок в Player / постройка при выбранной постройке; **СКМ в редакторе** — перетаскивание существа, клик без перетаскивания (порог 4 px) открывает окно-инспектор; V — выбросить предмет. Хелперы `cursor_world_pos`/`cursor_world_tile` используют луч активной камеры и пересечение с рельефом.

### 4.1. Фикс-степ тик

```rust
// Лимит тиков на кадр — функция скорости: столько тиков нужно, чтобы
// выдержать множитель даже на MIN_SIM_FPS = 5 кадрах в секунду
// (x1 -> 4, x100 -> 400). Симуляция не замедляется вместе с FPS
// (в т.ч. в неактивном окне на 10 FPS); ниже 5 FPS — замедляется.
pub(crate) fn max_ticks_for_frame(speed: SimSpeed) -> u32;

pub(crate) fn step_ticks(acc_seconds: f32, speed: f32, delta_secs: f32, max_ticks: u32) -> (u32, f32) {
    let mut acc = acc_seconds + delta_secs * speed;
    let step = 1.0 / TICKS_PER_SEC as f32;
    let mut ticks = 0;
    while acc >= step && ticks < max_ticks {
        acc -= step;
        ticks += 1;
    }
    if ticks == max_ticks { acc = 0.0; } // остаток отбрасывается — мир замедляется, а не зависает
    (ticks, acc)
}
```

На x20 при 60 FPS требуется ~6.7 тика за кадр; на x100 при 5 FPS — 400. Ниже 5 FPS симуляция замедляется, а не зависает.

`tick_world` за тик: `clock.tick_once()` → `sched.run_tick` (сработавшие задачи собираются) → `world.tick_entities(tick, controlled)` (FSM + ИИ людей) → `world.tick_projectiles(tick)` → `world.tick_item_entities(tick)`; после цикла — обработка задач (календарь перезапускается на следующую границу, растительность через `apply_task`), dirty-тайлы изымаются рендером. Захваченное существо делает `actions::step_direction` + `actions::tick_hunger` на каждый тик; смерть → дроп лута → наблюдатель. `apply_commands` передаёт в `apply_all` `state.controlled` как актора команд `Player*`. Пауза (ручная, по потере фокуса, в меню) — аккумулятор не растёт.

### 4.2. Undo в редакторе

Планируется ограниченный стек отмены для действий «бога» (правки тайлов, спавн/удаление объектов и существ, изменение ресурсов). Требования:

- только действия редактора (не действия игрока и не ход симуляции);
- ограниченный размер стека (например, 100 операций или до последней паузы);
- каждая запись хранит **инверсное** действие (например, `SetTerrain { pos, old }`) + исходный `Command`;
- при загрузке/новом мире стек очищается;
- undo выполняется через ту же `CommandQueue`, что и обычные действия — детерминизм и тестируемость сохраняются;
- при откате команды редактора перезапускают `vegetation::after_tile_changed` (см. 2.5).

Реализуется на этапе «Инфраструктура и качество» (см. `ROADMAP.md`).

## 5. Рендеринг

- Состав модуля: `terrain.rs` (сборка мешей блоков, LOD, dirty-перестройки, атлас), `sprites.rs` (объекты/предметы/культуры/существа, контуры, вспышки урона, счётчики), `hologram.rs` (голограмма строительства) + `isometric`/`textures`/`combat`/`lighting`/`lenses`.
- Мир нарезан на блоки 64×64 тайлов; **один 3D-меш на видимый блок** (`Mesh3d` + `StandardMaterial` с атласом). Ортографическая `Camera3d` всегда сохраняет изометрический ракурс; игровые спрайты — текстурированные 3D-quads с depth test, поэтому рельеф может закрывать их. Синхронизированная `Camera2d` рисует UI. Поворота камеры нет; в режиме наблюдателя СКМ перетаскивает существо.
- Каждый верх тайла — квадрат в 3D-сетке, который проецируется в ромб. `WORLD_TILE_SIZE = TILE_SIZE·√2` сохраняет прежний масштаб тайла в изометрическом ракурсе. Атлас 4×4 (14 видов тайлов) использует текстуры 32×32 из `assets/textures/tiles`, nearest sampling и гуттер 2 px; одна и та же полная текстура накладывается и на верх, и на боковые грани. Обратное отображение индекса атласа выводится из `TileType::from_discriminant` — новый вид тайла не требует правки рендера, но свою высоту (`tile_elevation`) и плоскость рей-пика (`intersect_terrain`) требует. Материал terrain — `unlit`: меш строится без атрибута нормали (сборка нормалей была ~2/3 стоимости пересборки блока), шейдер компилируется без `VERTEX_NORMALS`.
- **Визуальная высота** не хранится в симуляции: `rendering/isometric.rs` выводит её из `TileType` (глина и земля на одном уровне; вода/песок — базовый уровень; лес и камень выше; гора заметно выше). Верх поверхности направлен по +Z. Боковые грани строятся только по отрицательным X/Y — со стороны фиксированной камеры — и только там, где сосед ниже. Ray picking проверяет также эти грани и возвращает тайл-владелец поверхности. Видимость блоков определяется пересечением их 3D-границ с экранным viewport в координатах камеры.
- **LOD**: `lod = log2(2 px · scale / TILE_SIZE)`, до 6 уровней; в ячейке LOD — доминирующий тип тайла, его высота также задаёт силуэт рельефа. Переход LOD строится в скрытой сцене `incoming`; старая остаётся видимой до полного покрытия и переключается одним кадром без z-fighting. Видимые блоки проверяются по проецируемым 3D-границам с запасом 10 тайлов по viewport; новые блоки немедленно закрываются дешёвым одно-квадовым placeholder и заменяются полной геометрией в бюджете 4–32 блока за кадр, от центра экрана наружу.
- Dirty-тайлы разделены по каналам причины (`simulation/dirty.rs`): `terrain` (рельеф) → `rebuild_dirty_blocks` пересобирает затронутые блоки целиком (вне бюджета построения, с соседями у края блока — их боковые грани зависят от высоты); `decor` (объекты/предметы) → `refresh_decor` снимает детей блока (`despawn_related::<Children>`) и спавнит их заново, не трогая меш — геометрия рельефа не меняется. Декор рисуется только на LOD ≤ 1, на дальних блоках decor-события бесплатны.
- Объекты и предметы на земле — **дочерние спрайты сущности блока** (не по Bevy-сущности на тайл), только на LOD ≤ 1. Счётчики предметов — `Text2d`. Природные объекты — camera-facing спрайты; станции-постройки — изометрический блок из трёх квадов (верх + видимые грани −X/−Y, у печей фронт `front_on` при горении); костёр — крест из двух вертикальных квадов; склад — плоская декаль. Культуры — декалями на пашне. Дроп-сущности предметов (`item_entity`) — статичные billboard-спрайты с автоподбором.
- Объекты и существа — camera-facing 3D-quads с общим мешем и кэшированными материалами; неподвижные quads не требуют покадрового переориентирования. Динамические позиции выбираются лучом из камеры и пересечением с поверхностью рельефа. `EntitySprites { map: HashMap<id, Entity> }`, кадры анимации волка (2) и кролика (3 прыжковых) по состоянию, `flip_x` по направлению; позиция привязана к нижней границе непрозрачных пикселей текстуры. Человек временно рисуется текстурой игрока (`player.png`) в общем коде спрайтов существ — отдельного спрайта игрока больше нет.
- **Видимые области спрайтов (`EntitySpriteVisuals`)**: непрозрачные границы рисунка каждой текстуры существа считаются по альфа-каналу один раз (`scan_alpha_bounds`, прогревающая система — по мере загрузки ассетов, после полного прогрева бесплатна). Из них выводятся «ноги на землю» (сдвиг спрайта), зона пикинга `entity_at` и радиус контура — ручных констант видимой области больше нет, перерисовка спрайта не требует правки кода.
- **Выделение существа (редактор)**: белый контур (`update_selection_outlines`) — белый силуэт текстуры, **дилатированный** на радиус, соответствующий `OUTLINE_THICKNESS_PX` мировых пикселей при данном размере спрайта (сепарабельная дилатация O(пикселей), канвас с паддингом +2·радиус, кэш `WorldSpriteAssets.outlines`), позади спрайта по `EditorSelection::hovered`/`selected`. Квад контура — тот же `entity_transform`, что у спрайта, масштаб домножен на канвасные пад-факторы: внутренняя область канваса ложится на спрайт 1:1, кольцо везде одной мировой толщины и не зависит от положения рисунка в текстуре; только в наблюдателе, квад снимается вместе с причиной.
- **Голограмма строительства**: полупрозрачные квады той же геометрии, что у реальной постройки (крест костра, блок станции, декаль склада), зелёная/красная по `buildable_at` + `affordable` + `reachable` — только предсказание, финальную проверку делает симуляция.
- **Боевые визуализации (`rendering/combat.rs`)**: эффекты оружия по сообщению `WeaponFx` из ввода; предметы и снаряды размещаются в 3D и ориентируются под фиксированную камеру; привязка — к захваченному существу. Сохраняются дуга взмаха, выпад копья, лук на время кулдауна, тонкая стрела постоянной экранной толщины, летящее и воткнутое копьё, а также красная вспышка урона на 0.3 с.
- **Освещение (`lighting.rs`)**: ночь затемняет мир camera-space оверлеем из двух треугольников; фрагментный шейдер вычисляет затемнение каждого пикселя и квадратичный спад света `(1−d/R)²`: радиус костра — 5 тайлов, факела — 2.5, при этом максимум света в центре одинаков для обоих источников. Позиция факела обновляется не чаще 10 раз/с. Позиции, индивидуальные радиусы и силы огней передаются динамическим storage buffer и переводятся в плоскость камеры; буфер сортируется по X, и шейдер ищет «свои» огни бинарным поиском — стоимость фрагмента зависит от огней в его колонке, а не от всех костров. Отрисовка не зависит от шага сетки и сохраняет форму света при отдалении; отдельный проход UI остаётся незатемнённым. Реестр костров обновляется после применения команд редактора и до `render_world`, полный перескан — при `pending_rerender`. Настройка графики «Освещение» отключает систему целиком: оверлей скрывается и не собирается (вечный день).
- `textures.rs` — `TileTextures`: хэндлы 14 тайлов, объектов (включая пустую яблоню), станций (top/side/front/front_on — `StationTextures` по `BuildingKind`), креста костра, декаля склада, стадий культур, всех 91 предмета, игрока и волка. Стадии культур — плотный массив `[культура][стадия]` по чистой функции `crop_stage_slot` (несуществующие стадии — дубликат зрелой; раньше расхождение упаковки и адресации давало панику на картошке). Атлас 4×4.
- **Линзы карты (`lenses.rs`)**: подсветка чанков по `GameState::lenses` — «разумные существа» и «постройки» — только vertex-color terrain-квадов и отдельный `TerrainLensExtension` для terrain-материала. Его шейдер снижает контраст RGB на 25% только там, где vertex-color отмечает линзу; материал объектов, спрайтов и существ не меняется. Отдельных мешей, геометрии или высоты у линз нет, поэтому они не перекрывают другие слои и подсвечивают рельеф на любой высоте. Скан раз в секунду ограничен видимыми чанками; при включённых линзах LOD ограничен 4 (ячейка не больше чанка), чтобы цвет не пересекал границы чанков. Terrain-меши сохраняют атрибуты в MainWorld для выборочной перекраски изменившихся активных блоков.

> **LOD существ (в будущем).** По аналогии с блоками 64×64: чем меньше пиксель спрайта на экране, тем проще представление. Критерий перехода — «пиксель существа < реального пикселя на экране» (т.е. спрайт занимает меньше 1 физ. пикселя). Архитектурно — отдельный слой рендера сущностей, читающий позиции из `World::entities` без создания Bevy-сущностей для далёких/спящих; интерполяция только для видимых.

> **Солнце/луна/погода (в будущем).** Шейдерные эффекты поверх существующего оверлея тьмы. Архитектурно совместимо: `lighting.rs` уже считает альфу затенения по времени суток; солнце/луна — параметры для шейдера, туман — отдельный оверлей, тени — в будущем (потребует пересмотра структуры меша).

## 6. UI

- `bottom_panel/` — панель редактора (`mod.rs` — каркас и кнопки, `categories.rs` — содержимое подменю и названия для тултипов, `world_fields.rs` — поля мира) в духе WorldBox: два ряда кнопок 64×64 (пауза, скорость, 4 категории инструментов, линзы карты — с подменю); поля размера мира и сида (Enter — применить, Escape — отмена); Q — назад/сброс инструмента; скрывается в Player. Линзы (`PanelMenu::Lenses`) — независимые переключатели `GameState.lenses` («Разумные», «Постройки»), не инструменты: клик по карте ничего не ставит.
- `inventory/` — окно инвентаря (Tab; `mod.rs` — состояние и тоггл, `layout.rs` — построение окна, `craft_grid.rs` — сетка крафта, `drag.rs` — перетаскивание): слоты брони/одежды/баублов/misc (броня, одежда и косметика — столбцы слева, одежда между бронёй и косметикой), drag&drop со стеком «в руке», слот-мусорка под столбцом косметики (отступ пол-слота; перетаскивание стека в неё затирает прежнее содержимое, забрать ещё можно перетаскиванием), сетка крафта 3×3 (ЛКМ +1, ПКМ −1, Shift — стек/всё, удержание — заполнение проведением), слот результата. Shift+ЛКМ по результату — максимум крафтов (ингредиенты из сетки и инвентаря, с учётом места), Shift+ПКМ — половина максимума с округлением вниз (минимум 1). При закрытии сетка возвращается в инвентарь, невлезшее дропается на землю. Отпускание перетаскиваемого стека за пределами окна бросает его в мир в сторону курсора (команда `PlayerThrowStack`).
- `hotbar.rs` — 8 слотов внизу по центру, выбор цифрами 1–8 и Q/E; слоты совместимы с окном инвентаря (drag между ними работает) и перетаскиваются между собой прямо в режиме игрока без открытого инвентаря.
- `construction.rs` — меню строительства (C, только Player): список `ObjectKind::BUILDINGS` с ценами, **ПКМ** ставит `Command::PlayerBuild`. При выбранной постройке панель скрывается (`Visibility::Hidden`, состояние `open` не меняется) — место установки ищется по голограмме; ESC/C снимают выбор, повторные закрывают меню.
- `health.rs` — шкалы потребностей захваченного существа (только Player), снизу вверх: HP (максимум — по виду существа), голод (0xFF8844, у всех видов), броня (0xCCCCCC, рейтинг из надетой брони; у неразумного захваченного ряд скрывается). Здесь же кнопка «ИИ» (правый нижний угол, маркер `AiToggleButton` — обсервер и стили работают только с ней) — переключение автономности захваченного существа (см. 2.7).
- `menus/` — технологии (T) и институты (Y); `mod.rs` — тоггл и загрузка данных, `tech.rs`/`social.rs` — данные деревьев, `tree_view.rs` — общий движок дерева (раскладка, отрисовка, обзор, валидация): **полноэкранные деревья слева-направо** из `data/science/tech_*.json` / `data/culture/social_*.json`. Деревья ветвятся: основная последовательная цепочка задаёт эпохи, боковые ветви требуют узлы цепочки и раскладываются в те же колонки глубины (сайд-узлы не должны выходить за колонки своей эпохи); границы эпох отмечены вертикальными светло-серыми линиями (позиции разделителей — константы `TECH_ERA_COLUMNS`/`SOCIAL_ERA_COLUMNS` в коде, правятся вместе с данными). Фон — `menu_bg.rs`: текстура `assets/textures/ui/bg.png` подгоняется под окно режимом cover (обрезка до пропорций + масштаб, ближайший сосед); копия собирается заранее — при старте, как только исходник загрузится, и далее только при изменении размера окна — и кешируется в `MenuBgCache`, в остальное время рисуется без пересборки. Глухой фон закрывает собой мир и остальной UI; корни слева, ветви — по колонкам глубины; соединители — гладкие кубические Безье (полилиния из 11 повёрнутых через `UiTransform` сегментов, приём из бестиария Endless_Space). Раскладка карточек и линий переписывается только при сдвиге вида (панорама/зум), а не каждый кадр — иначе зря грязнятся тысячи UI-узлов. Зум колесом к курсору, панорама зажатой ПКМ, текст прячется по порогам зума; вид (зум/сдвиг) не сохраняется — ресурс `TreeView` создаётся при открытии и удаляется при закрытии. Позиции ввода камеры/игрока при открытых модалках блокируются.
- `creative.rs` — творческое меню (I, бинд «Творческое меню»): плитки всех предметов `ItemKind::ALL`, слоты как в инвентаре, счётчик = максимальный стак; клик — полный стак в инвентарь захваченного существа (остаток при переполнении игнорируется). Доступно в обоих режимах при захвате разумного существа; закрывается общей ESC-цепочкой. Окно фиксированной высоты (79% экрана — на плитку ниже прежних 85%), список плиток прокручивается колесом (система `scroll_creative_grid` ведёт `ScrollPosition` вручную и зажимает по размеру содержимого). Наверху строка поиска (`TextInput`): ряды плиток пересобираются по подстроке названия предмета. Наведение на плитку + цифра 1–8 кладёт полный стак предмета в соответствующий слот хотбара. При наведении на плитку показывается тултип с названием предмета. Стек, перетащенный из хотбара и брошенный над панелью, удаляется (как в Minecraft).
- `pause_menu.rs` + `settings_window.rs` — ESC-меню: сохранение/загрузка (4 слота с датой из заголовка), настройки в `settings_window.rs` (геймплей, графика, звук — 5 слайдеров, управление — 13 биндов с захватом клавиш), сброс настроек. Единая цепочка ESC: открытое меню → родитель → закрыть (пауз-меню ставит паузу, закрытие снимает).
- `fps.rs` — FPS, игровая дата (год, сезон, день, ЧЧ:ММ), температура в точке игрока (`ambient_temperature_c`, пока заглушка 24 °C). F3 включает расширенный режим: + время тика (мс), оценка ОЗУ мира в МБ и байтах на тайл (`World::memory_bytes`, ARCHITECTURE 3.1) и метрики рендера (`RenderMetrics`).
- `tooltip.rs` — тултипы предметов с русскими названиями из `info/items.json`: слоты инвентаря, клетки крафта, слот результата крафта, хотбар и плитки творческого меню.
- `style.rs` — палитра Dark Material UI; `icons.rs` — `UiIcons` (тайлы, объекты, предметы, слоты брони, play/pause), пиксель-арт с `nearest()`.
- `stations/` — GUI рабочих станций (сплит монолита `station.rs`) (ПКМ по станции **в радиусе взаимодействия**, ESC и Tab закрывают; при отдалении игрока окно закрывается само): слоты контейнера станции + MISC игрока как хотбар (броня/одежда/косметика недоступны). Перенос — командой `StationMoveItem` (клик-источник → клик-цель — весь стак, Shift — быстрый перенос, ПКМ — половина). Печи — раскладка в стиле Minecraft: вход, под ним индикатор пламени и топливо, посередине стрелка прогресса готовки (заливка по `cook_finish_tick`), справа увеличенный слот результата; зола — отдельным рядом. Перетаскивание стеков мышью в/из всех слотов, кроме выхода (misc↔misc — напрямую, с контейнером — командой `StationMoveItem`); отпускание за пределами окна бросает стек в мир в сторону курсора. ЛКМ по выходному слоту забирает весь стек, цифры 1–8 при наведении перекладывают стек между хотбаром и слотом под курсором и работают в обе стороны (повторное нажатие забирает предмет обратно; при занятых обоих — обмен; выбор слота хотбара цифрами в GUI заблокирован, Q/E работают). Пустые слоты станций показывают тултипом свою роль («Топливо», «Топливо: только уголь», «Результат — забирать», …). Верстак/кузнечный стол — временная UI-сетка 3×3 (+4 слота инструментов кузнечного стола), верстак наследует ручные рецепты, содержимое сетки возвращается в инвентарь при закрытии. Переключение ПКМ на другую станцию сносит старое окно сразу.
- `inspector.rs` — окно-инспектор существа (редактор): открывается СКМ-кликом без перетаскивания (`editor_entity_drag`, порог 4 px; перетаскивание начинается только после превышения порога — клик не телепортирует существо) по существу в радиусе 2 тайлов от курсора; показывает полосы HP (максимум по виду)/голода/брони над заголовком и весь инвентарь существа с перетаскиванием предметов (призрак стека, как в станциях). Перенос — `Command::EntityMoveItem` (правила `Inventory::transfer`), выброс за окном — `Command::EntityDropItem` (предмет падает под существом). Неразумное существо — только HP. Живёт в наблюдателе, закрытие — ESC-цепочка/повторный клик/удаление существа/смена режима; подсветка — белый контур (см. рендер).
- Общие утилиты: `text_input_focused` (хоткеи при наборе текста не срабатывают), `BlocksWorldInput`, `cursor_over_ui` (скрытые узлы `Visibility::Hidden` ввод не перехватывают).

## 7. Данные

- `data/science/tech_*.json` (по файлу на эпоху: stone/bronze/iron/medieval, 56 технологий), `data/culture/social_*.json` (44 института) — id, name, era, requires, description; основная цепочка задаёт эпохи, боковые ветви требуют узлы цепочки; грузятся при старте (файлы эпох сливаются в лексикографическом порядке), ошибки — warn и пустые данные. После загрузки данные валидируются (`validate_tree`): дубликаты id, неизвестные требования, циклы — warn-лог, игра не падает.
- `data/crafts/*.json` — 14 ручных рецептов (6 каменных инструментов, удочка, верёвка, волокно, лук — 2 зеркальные сетки, стрелы, связка палок — 2 взаимных рецепта 8 палок ↔ связка). Станции в подпапках: `crafting_table/` (молот каменный, книга, бумага, оперение), `furnace/` (готовка еды, обжиг кирпича, древесный уголь), `blast_furnace/` (руда → слитки), `smithing_table/` (8 медных инструментов с `tools: ["hammer_stone"]`). Восемь рецептов еды общие для печи и костра (`parent: ["furnace", "campfire"]`), поэтому отдельных файлов `campfire/` нет. Крафтов самих станций пока нет.
- `info/items.json` — русские названия предметов для тултипов.
- План (GAME_DESIGN 7): lazy-load станционных рецептов по счётчику активных станций, индекс «предмет → станции»; валидация JSON в debug.

## 8. Тесты

`src/tests/` — по модулю на домен, без графики (`cargo test`): `armor`, `build`, `climate`, `clothes`, `containers`, `crafts`, `crops`, `entities`, `generation`, `item_entity`, `player`, `rendering`, `save`, `time_scheduler`, `vegetation`, `world`. Покрывают: сжатие чанков и слои, часы и переходы календаря, климат (сезонный/суточный ход, непрерывность), планировщик (порядок, отмена), фикс-степ (лимит), генерацию (детерминизм, деревья/кусты/валуны/яблони, реки), растительность, крафт (shaped/shapeless/валидация, массовый крафт с добором из инвентаря и учётом места, взаимный рецепт связки палок), реестр предметов (уникальные id, дискриминанты и обратные преобразования), инвентарь (включая мусорку и правила слотов брони и одежды), голод (расход по активности, урон от голода, еда, кулдаун), броню (защита, рейтинг, линейное поглощение), одежду (тепло только из надетых слотов), поведение существ (включая перенос командой редактора), roundtrip сохранений (включая игрока с кольчугой, секцией одежды и мусоркой; отказ на чужом предмете в слоте одежды). Рендер — только структуро-независимые проверки.

## 9. Профилирование и метрики

Обязательный минимум на экране:
- FPS;
- время тика (мс) — сглаженное (`TickTiming`);
- игровая дата/время;
- температура в точке игрока;
- текущий размер мира и seed.

Дополнительно (по мере роста нагрузки, выводится по хоткею):
- число активных сущностей (`EntityStore::len`);
- число активных процессов в планировщике (near+far);
- объём копируемых за кадр данных;
- dirty-события по каналам (terrain/decor), перестройки блоков и время сборки мешей — уже выводятся в FPS-панель из `rendering::RenderMetrics` (сбрасывается панелью каждые 0.5 с), вместе с числом видимых блоков и спрайтов.

Цель — иметь возможность профилировать любую систему без встраивания профайлера. Все счётчики — только для отладки, на симуляцию не влияют.

## 10. Ограничения и принципы контента

Архитектурно значимые запреты и рамки (см. также `GAME_DESIGN.md` п.2):

- **Никакой магии** ни в одном слое (визуал, знания, институты). Всё «сверхъестественное» — только режим «бога» как игровое допущение.
- **NSFW запрещён.** Контент игры должен соответствовать общепринятым этическим нормам; реальные спорные/чувствительные темы не затрагиваются (или реализуются в обобщённом виде без привязки к реальности).
- **Моддинг** пока не предусмотрен. Всё, что читается из `data/`, всё равно валидируется при старте — на случай ручной правки разработчиком.
- **Кроссплатформенный детерминизм** — цель, но не обязательство (см. 2.13). При добавлении платформо-зависимых фич (файловая система, время, RNG) — проверять, что симуляция не полагается на их поведение.
- **Память** — учитывать при добавлении новых слоёв и полей: рост на байт на тайл при большой карте критичен. Новые поля — только с обоснованием (см. 3.1).

## 11. Соглашения

- Комментарии — на русском, для каждой функции: что делает и зачем. Идентификаторы — на английском.
- `cargo check`, `cargo clippy`, `cargo test` — обязательны. `cargo fmt` не используется.
- Новые зависимости — только с разрешения автора.
- Правила совместимости: новые `TileType`/`ItemKind`/`ResourceKind`/`ObjectKind` — только в конец enum; кодировка `TaskKind` в сохранениях — явные теги.
